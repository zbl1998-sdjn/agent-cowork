# Agent Cowork 面试演示与上线预备验收标准

> 本文件是验收合同,不是路线图,也不是当前状态报告。任何功能是否可以用于面试演示或未来上线,以本文件的判定为准。

## 0. 总原则

Agent Cowork 的验收目标不是"找不到任何小问题",而是:

> 核心用户旅程在真实安装版、真实模型、真实文件、重启恢复、失败分支下都可完成;P0/P1 为 0;剩余问题都有分级、证据、绕过方式和延期版本。

面试演示尤其严格:

> 任何需要现场解释"这个其实是因为..."的问题,都不得进入 Demo Ready。

## 1. 判定档位

| 档位 | 判定条件 | 可对外表述 |
| --- | --- | --- |
| Not Ready | 存在任一 P0,或安装版核心路径未验收,或门禁不绿,或文档与证据冲突 | 不可演示为完整产品 |
| Demo Ready | P0/P1 为 0;核心面试脚本连续 3 轮通过;所有不可用入口已隐藏或明确标注 | 可用于面试现场演示 |
| Beta Ready | Demo Ready + 真实环境矩阵覆盖主要失败分支;P2 有已知问题清单 | 可给小范围用户试用 |
| Release Ready | Beta Ready + 签名、更新、数据迁移、安全、隐私、回滚、发布产物证据完整 | 可准备正式上线 |

不得用"本地 dev server 可用"替代 Demo Ready,也不得用 `npm run check` 通过替代安装版验收。

## 1.1 外部基准映射

本标准按下列外部基准校准。外部基准只给原则,本文件把原则落到 Agent Cowork 的具体验收项。

| 基准 | 本项目采用的验收含义 |
| --- | --- |
| ISO/IEC 25010 产品质量模型 | 功能正确性、可靠性、可用性、性能、安全、兼容性、可维护性、可移植性都必须有验收项,不能只验 happy path |
| OWASP ASVS | 本地 HTTP/SSE API、鉴权、会话、输入校验、错误处理、文件上传、日志脱敏、安全配置必须有可复现检查 |
| OWASP Top 10 for LLM Applications | prompt injection、敏感信息泄漏、工具越权、过度代理、供应链和资源耗尽必须进入红队验收 |
| NIST SSDF SP 800-218 | 发布前必须有安全需求、代码审查/测试、漏洞处理、供应链和可追溯发布证据 |
| NIST AI RMF / Generative AI Profile | 真实模型能力必须有风险识别、失败模式、人工确认、日志和回退策略,不能把 AI 输出当确定性事实 |
| Tauri v2 安全/更新机制 | capability 最小化、CSP、sidecar 边界、updater 签名和 release endpoint 不能是装饰性配置 |
| Microsoft Windows 桌面应用质量/隐私要求 | 安装、卸载、更新、崩溃、数据保留、隐私说明、用户控制和系统兼容性必须能自证 |
| WCAG 2.2 / Windows 可访问性实践 | 键盘可达、焦点可见、可读对比度、控件名称和错误提示是验收条件,不是 UI polish |

## 2. 严重度定义

| 等级 | 定义 | 验收要求 |
| --- | --- | --- |
| P0 Blocker | 面试现场会直接露馅;核心功能不可用;数据丢失;假成功;无法启动/登录/恢复;安全边界绕过 | 必须修复并复测,否则 Not Ready |
| P1 Major | 核心路径可走,但状态误导、失败无提示、恢复不可靠、后台行为与 UI 不一致 | Demo Ready 前必须清零 |
| P2 Minor | 不阻断主演示路径,但影响体验、低频边界、可诊断性或文案 | 可延期,但必须记录 |
| P3 Polish | 视觉、排序、微交互、非核心优化 | 不阻断 Demo Ready |

所有问题必须归入一个等级。不能用"大概没事"或"演示时避开"跳过 P0/P1。

## 3. 一票否决项

出现任一项,直接判 Not Ready:

- 应用启动后 host 未拉起、端口冲突无法自愈、白屏、按钮无响应、登录页假可用。
- 上一次对话无法承接,或重启后历史丢失、消息顺序错乱、active conversation 错位。
- 文件显示已上传,但模型实际未拿到文件;或上传失败没有明确提示。
- 点击停止后 UI 显示已停止,但后台仍生成、继续调用工具或继续写文件。
- 审批、apply、rollback、取消出现假成功、卡住、重复执行、无提示失败。
- provider/model/API key/baseUrl 配错时,表现为无响应、空结果、泛化错误或误导性成功。
- 工具调用失败、超时、预算中止、安全拦截、fallback、checkpoint 失败等关键事件没有展示给用户。
- 工作区选择看起来成功,但实际因为 path jail、权限、盘符、junction、长路径或中文路径不能用。
- 定时任务、recipe、运行时依赖、更新检查等 UI 展示为可用,但实际是 no-op、placeholder 或只生成计划。
- 安装版和 dev 版核心路径表现不一致,且没有明确记录和用户提示。
- 文档声称完成,但 smoke/report/真实安装版证据显示未完成。
- `npm run check` 不绿,或 release/demo 候选树存在不明 dirty/untracked 文件。
- 任何核心失败只能靠终端解释,用户界面没有可理解的原因、下一步和重试方式。
- 关键操作不能仅靠鼠标完成,或焦点丢失导致键盘用户无法继续演示。
- 长任务、长会话、多文件场景下出现明显卡死、内存持续上涨、窗口无响应或流式输出断裂。
- AI 读取不可信文件后绕过审批、执行未批准工具、泄漏 secret、或把外部内容当作系统指令。
- 发布候选缺少依赖清单、签名/来源说明、漏洞处置记录或可回滚产物。

## 4. Demo Ready 硬门槛

Demo Ready 必须同时满足:

- `npm run check` 全绿。
- `npm test` 全绿,或失败项被证明为环境问题并有替代验收证据。
- 使用安装版或等价 Windows 桌面构建演示,不只使用 Vite/dev server。
- 真实模型路径可用;如果演示离线模式,必须明确隐藏或标注模型能力不可用。
- 真实工作区、真实文件、多文件上传、审批写入、产物打开路径跑通。
- 关闭应用再打开后,能恢复上一次 active conversation、workspace、会话列表和必要 run 状态。
- 核心演示脚本连续 3 轮通过,每轮产出时间戳报告或人工验收记录。
- 演示脚本上的每个按钮、面板、入口都是真的可用;不可用功能必须隐藏、禁用或明确标注"待验收"。
- 所有核心失败都有 UI 提示,不能静默失败、假空列表、假成功或按钮无反应。
- 演示脚本全程可用键盘完成主要操作,焦点、快捷键、弹窗和错误提示不丢失。
- 演示过程中窗口不能卡死;长会话、流式输出、多文件上传和产物面板必须保持可交互。
- 演示用文件中加入一条恶意提示注入样本时,agent 不得绕过审批、泄漏配置或执行未批准工具。

## 5. 必验核心用户旅程

### 5.1 首次启动与 host 生命周期

必须覆盖:

- 首次打开安装版。
- host sidecar 自动启动。
- 端口 3017 被占用。
- host 启动慢、启动失败、健康检查失败。
- 退出应用后 sidecar 清理。
- 重启应用后恢复状态。

通过标准:

- 用户能清楚看到当前状态。
- host 不可用时不能进入假可用工作台。
- 失败时提供原因、日志位置和重试入口。

### 5.2 模型配置与 provider 切换

必须覆盖:

- Kimi/OpenAI/Claude/local provider。
- 正确 key、空 key、错误 key、错误 baseUrl、网络失败。
- 本轮 BYO-key 不持久化。
- 全局设置和本轮设置的优先级。
- provider fallback 触发和不触发条件。

通过标准:

- 配置错误必须明确显示为配置错误。
- key/baseUrl 不回显、不入日志、不进入报告。
- UI 展示的 provider/model 与 run record 归因一致。

### 5.3 对话承接与历史恢复

这是 P0 验收项。

必须覆盖:

- 新建对话。
- 继续上一次对话。
- 切换历史会话。
- 关闭应用后重新打开。
- 登录前本地历史与登录后远端历史。
- 长对话超过截断上限。
- 带附件、工具结果、审批状态的历史。

通过标准:

- 默认回到上一次 active conversation。
- 消息、附件引用、工具结果、审批状态不无声丢失。
- 如果历史被压缩或截断,必须明确提示。
- 本地历史和远端历史不能无提示互相覆盖。
- 快速切换会话不能把 A 会话内容加载到 B 会话。
- 保存失败必须提示,不能假装已保存。

### 5.4 文件上传与文件上下文

必须覆盖:

- 单文件、多文件、重复文件。
- 大文件、超总量、超数量。
- 不允许的扩展名。
- 中文路径、长路径、空文件、被占用文件。
- 上传后模型引用文件内容。
- 上传失败后的重试和附件保留。

通过标准:

- 用户消息不能声称上传成功而实际失败。
- 上传失败不能清空用户已选文件。
- 模型实际收到的文件列表必须可追踪。
- 超限和不支持类型必须有明确中文提示。

### 5.5 Agent 执行、流式输出和取消

必须覆盖:

- 普通问答。
- 工具调用。
- 长任务流式输出。
- 手动停止。
- 模型超时。
- 网络中断。
- budget guard 中止。
- checkpoint/resume。

通过标准:

- UI 状态必须和后端 run 状态一致。
- 停止必须真正取消或明确说明取消失败。
- 后台不能在 UI 显示已停止后继续写入。
- 失败、取消、超时后必须能继续、重试或明确结束。

### 5.6 审批、apply、rollback

必须覆盖:

- 单个审批。
- 批量审批。
- 拒绝审批。
- 审批过期。
- apply 成功。
- apply 失败。
- rollback 成功。
- rollback 失败。
- 重复点击、刷新后继续。

通过标准:

- 所有写操作必须经过审批或明确的安全策略。
- apply 成功才显示完成。
- apply 失败必须进入失败态,不能停留在待审批假状态。
- rollback 失败必须保留可诊断信息。
- 重试不能重复执行已完成副作用。

### 5.7 工作区与路径安全

必须覆盖:

- 默认 trusted root。
- 用户选择子目录。
- D 盘目录。
- 外置盘或网络盘。
- 越权路径。
- symlink/junction。
- 中文路径和长路径。
- 权限不足目录。

通过标准:

- UI 必须说明工作区是否在 trusted root 内。
- 被 path jail 拒绝时必须解释原因。
- 所有打开文件、产物、审计记录都不能越界。
- 看起来可选但实际不可用的目录,必须在选择时就提示。

### 5.8 Recipe 与产物

必须覆盖:

- 有输入文件的 recipe。
- 无输入文件的 recipe。
- 无 operations 的 recipe。
- 失败 recipe。
- 需要审批的 recipe。
- 产物打开、重命名、刷新、删除或保留策略。

通过标准:

- 无 operations 不能显示成等待审批。
- recipe 缺输入时必须明确提示需要哪些 sources。
- 产物真实存在于磁盘且可打开。
- 打开失败必须提示,不能按钮无反应。

### 5.9 定时任务

必须覆盖:

- recipe 定时任务。
- prompt-only 定时任务。
- 立即执行。
- 取消任务。
- 重启后保留。
- 执行失败。

通过标准:

- prompt-only 如果未实现,不得显示为可成功执行。
- 任务是否创建、是否执行、是否失败必须可见。
- 重启后任务状态必须一致。

### 5.10 运行时依赖、连接器与更新

必须覆盖:

- 缺失依赖检测。
- 安装计划、清理计划、更新计划。
- 真实可执行动作和 plan-only 动作的区分。
- GitHub OAuth 未配置、授权、撤销。
- MCP 连接、断开、工具撤销。
- 更新检查。

通过标准:

- 只生成计划的功能不能写成已经安装、已经清理或已经更新。
- placeholder endpoint 不得作为可用更新功能展示。
- 连接器撤销后工具必须不可再调用。
- OAuth 缺配置必须显示为配置缺失,不是授权失败。

### 5.11 可观察性、日志与导出

必须覆盖:

- run 列表。
- run 详情。
- token/cost/provider 归因。
- tool why/result/error。
- 安全拦截。
- checkpoint 保存失败。
- 日志导出。

通过标准:

- 用户能看到任务为什么失败。
- 开发者能从报告或日志定位 runId、provider、workspace、错误类型。
- 敏感信息必须脱敏。

### 5.12 可访问性、键盘和现场可操作性

必须覆盖:

- 只用键盘完成登录/游客进入、选择会话、发送消息、上传文件、审批、打开面板、关闭弹窗。
- 焦点在弹窗、侧边面板、审批控件、错误态、文件选择失败后仍可预测。
- 主要按钮和 icon-only 控件有可访问名称。
- 文本、错误、状态徽标、禁用态有足够对比度。
- 加载、失败、成功、取消、待审批状态不只靠颜色表达。
- 150% 缩放、Windows 中文字体、窄窗口下文字不重叠。

通过标准:

- 面试现场不用解释"这个只能鼠标点"或"这里焦点丢了"。
- 键盘用户不会被困在弹窗或侧边栏。
- 错误提示能被视觉和辅助技术同时识别。

### 5.13 性能、资源和降级

必须覆盖:

- 冷启动到可交互。
- host 启动到 `/health` ready。
- 首条 token 延迟。
- 长会话 200+ messages。
- 多文件上传和搜索。
- 产物面板、可观察性面板、连接器面板懒加载。
- 连续 30 分钟演示。
- 网络断开、模型慢响应、API rate limit。

通过标准:

- 启动、首屏、首 token、取消响应、面板打开必须有目标阈值和实测值。
- UI 不能因流式 token 或长列表持续重渲到不可交互。
- 内存、句柄、sidecar 进程数量不能持续增长。
- 外部服务慢或不可用时,本地文件能力仍能工作并明确降级。

### 5.14 AI/LLM 红队与工具安全

必须覆盖:

- 文档内 prompt injection。
- 工具结果内 prompt injection。
- 要求泄漏 API key、token、路径、系统提示。
- 要求绕过审批直接写文件、删文件、执行 shell、外传数据。
- 模型生成错误 JSON/tool args。
- 模型重复调用同一工具。
- 高成本/无限循环任务。
- provider fallback 期间的安全策略继承。

通过标准:

- 不可信内容必须作为数据处理,不能提升为系统指令。
- 任何写入、删除、执行、外联都必须走风险分级和审批。
- 拒绝和拦截必须向用户解释,并写入 run trace。
- 红队样本必须进入自动化 eval 或 smoke,不能只靠人工记忆。

### 5.15 供应链、安装器和发布来源

必须覆盖:

- npm/root/UI/host 依赖清单。
- Rust/Tauri 依赖清单。
- sidecar/embedded runtime 来源。
- 安装包签名。
- updater 签名和 endpoint。
- release bundle、manifest、tag、CHANGELOG 一致性。
- 高危依赖、过期依赖、license 风险。
- 离线安装、升级、卸载、回滚。

通过标准:

- 发布候选必须能说明"这个二进制从哪里来、由什么源码构建、依赖是什么、如何回滚"。
- 任何外部下载组件都必须有来源、hash/signature policy 和失败关闭策略。
- 没有真实 update endpoint 时,更新入口不能被当作可用功能演示。

### 5.16 MASE 记忆治理(召回 / 写入 / supersede / 时间线 / 崩溃安全)

这是 P0 验收项,且与 5.3 强相关:5.3 的跨轮记忆实际由 MASE 注入支撑,本节单独验收 MASE 作为记忆后端在安装版、真实模型下的正确性。

必须覆盖:

- 写缝:一轮对话后,用户输入被记为事件日志(role 正确),其中显式事实被抽取并 upsert 进当前事实,并带 source_log_id + reason 可溯源。
- 读缝:下一轮请求注入三层记忆——【当前事实】(全量、与措辞无关)、【最近对话】(按 thread 时序)、【相关历史】(BM25 召回)。
- 召回有效性:模型能据此回答"第一句是什么""刚才/继续上文""某个事实现在是多少"。
- supersede:同一 key 改值时,当前值更新为新值,旧值进入历史并打 superseded_at;不是删除,也不是追加成重复事实。
- 检索为空:相关记忆查不到时明确说明"没有",不得编造未提及的信息。
- 作用域:不同会话线程(当前按 tenant/user)互不串味;窗口级精确隔离若未实现,必须在文档与行为上标注为已知限制。
- 崩溃安全:写入后强杀 host / 断电式重启,已确认的记忆不丢、库不损坏、重启后仍可召回(WAL)。
- 降级:MASE 未启用、不可达或响应慢时,读缝短超时降级为"本轮不带记忆"且对话不卡死,写缝失败不阻断回复。
- 注入预算:注入的记忆有上限,长会话不会让记忆块无界膨胀挤占上下文。
- 隐私:记忆库位置可知、可导出、可删除;key/token 等敏感值不得被当作"事实"长期留存。

通过标准:

- 第二轮能拿到第一轮写入的事实(当前事实命中,或历史/时间线召回命中)。
- 改值后,回答与 UI 以最新值为准,并能追溯到旧值与变更来源(source_log_id)。
- 召回为空时回答"无",不编造;红队问一条"我之前说过、其实没说过"的事实时不被诱导承认。
- 强制重启(含 host 被杀)后,已确认记忆仍可召回,且无数据库损坏报错。
- MASE 慢/挂时对话仍可进行,并明确标为"本轮无记忆",绝不静默卡死或假装记得。
- 记忆类失败(写入失败、召回超时、supersede 冲突)有 run trace / 日志可定位。
- 跨会话不串味;窗口级隔离若为 TODO,文档明记,演示不宣称已按窗口隔离。

## 6. 上线预备硬门槛

Release Ready 在 Demo Ready 基础上额外要求:

- 安装包签名完成,不能是 `NotSigned`。
- 自动更新 endpoint 真实可用,不能是 placeholder。
- 版本号、CHANGELOG、tag、release bundle、安装包、manifest 一致。
- 升级保留用户数据、组件、缓存和历史。
- 卸载清理有用户确认,且不会删 trusted root 或用户工作区。
- 数据持久化有迁移策略、备份策略、容量上限提示。
- 所有外部调用都有 timeout、bounded retry、错误分类和用户提示。
- secret scan、依赖安全扫描、license/合规检查通过。
- 生成并归档 SBOM 或等价依赖清单,覆盖 Node/UI/Rust/Tauri/sidecar/embedded runtime。
- 发布产物有来源追踪:commit、tag、bundle、installer、manifest、签名证据一致。
- 有漏洞接收和处置口径:安全问题如何报告、如何分级、如何修复和发布。
- 安全边界有回归测试:path jail、auth、CORS、rate limit、body limit、redaction、approval。
- 隐私策略清楚:默认本地、默认不外发、遥测 opt-in、可删除记忆。
- 用户数据控制清楚:导出、删除、清理、卸载保留/删除、日志脱敏。
- 可访问性检查通过:键盘、焦点、对比度、控件名称、缩放不重叠。
- 性能和资源预算有实测报告:启动、首 token、长会话、内存、CPU、sidecar 进程清理。
- 安装版在真实 Windows 环境通过 smoke,包括 WebView 深交互。

## 7. 验收证据要求

每条验收记录至少包含:

| 字段 | 要求 |
| --- | --- |
| 版本 | commit hash、tag 或构建号 |
| 环境 | Windows 版本、安装路径、Node/host 形态、store backend |
| 命令 | 实际执行的命令或人工操作步骤 |
| 输入 | workspace、文件类型、provider、是否真实 key |
| 预期结果 | 用户应看到什么 |
| 实际结果 | 真实结果,含失败 |
| 证据 | JSON report、截图、日志、runId、artifact 路径 |
| 判定 | Pass / Fail / Not Implemented / Deferred |
| 严重度 | P0 / P1 / P2 / P3 |
| 后续 | 修复项、负责人、计划版本 |
| 外部基准 | 对应 ISO/OWASP/NIST/Tauri/Microsoft/WCAG 条目或本文件章节 |

`Deferred` 只能用于 P2/P3,不能用于 P0/P1。P0/P1 未修复时只能判 Not Ready。

## 9. 演示脚本验收规则

正式面试前至少连续跑 3 轮:

1. 打开安装版。
2. 确认 host ready。
3. 恢复上一次 conversation。
4. 新建一轮真实模型对话。
5. 上传多个真实文件。
6. 让 agent 生成计划。
7. 审批一个文件写入或产物生成。
8. 打开产物。
9. 停止一次长任务并确认后台停止。
10. 用键盘打开一次设置或侧边面板并返回主流程。
11. 注入一个含 prompt injection 的测试文件,确认不会绕过审批或泄漏配置。
12. 关闭应用。
13. 重新打开并确认历史、workspace、产物和 run 状态仍在。

3 轮中任一轮出现 P0/P1,Demo Ready 失效。

## 10. 未完成功能的展示规则

未完成或未真实验收的功能只能有三种处理:

- 隐藏入口。
- 禁用入口并显示"待验收/需配置"。
- 保留入口但明确标注 plan-only 或 preview-only。

禁止:

- 用可点击按钮包装 no-op。
- 用成功 toast 掩盖失败。
- 用空列表代表加载失败。
- 用 dev-only 能力冒充安装版能力。
- 在文档中把本地可测子项写成真实环境已完成。

## 11. Bug 修复的完成定义

每个 P0/P1 bug 修复必须满足:

- 有最小复现步骤。
- 有根因说明。
- 有针对性测试或 smoke。
- 有安装版或真实环境复测证据,如果问题发生在这些环境。
- 有回归风险说明。
- 验收记录从 Fail 更新为 Pass。

只修代码、不复测,不算完成。

## 12. 当前项目使用口径

后续所有审查、修复、发布、面试准备都按本文件判定:

- 发现 P0/P1:优先修,不得延期到演示后。
- 发现 P2/P3:进入已知问题清单,不得混入 Ready 判定。
- 文档、报告、smoke 和真实安装版不一致:以真实安装版和最新 smoke 证据为准。
- 无证据的完成声明无效。
